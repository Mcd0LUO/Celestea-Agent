# Studio 会话持久化评估（刷新后聊天消失问题）

> 📦 历史文档（2026-09-11 归档）：描述的是「刷新后聊天消失」的评估与推荐方案 A，该方案早已实现，属已被取代的事实。当前权威入口见 [../DEVELOPMENT.md](../DEVELOPMENT.md)。

- 评估人：架构师会话（实测证据）
- 日期：2026-09-07
- 结论先行：**后端已持久化，缺口在前端启动恢复**。刷新丢的不是数据，是 UI 没有"加载历史"这一步。推荐方案 A（启动时拉取历史渲染），半天级工作量。

---

## 1. 现状事实（全部实测）

| 层 | 事实 | 证据 |
|---|---|---|
| 后端落盘 | `CELESTEA_SESSION_DIR=/src/celestea_studio/sessions`，`cli-main.jsonl` 143 行 / 24.7KB，PersistentSessionLog 每事件 flush | `ls -la sessions/`、`wc -l cli-main.jsonl` |
| 后端回放 | 进程重启时 compose 重放 jsonl → 历史在重启后仍在 | 多次重启后 `/api/sessions/cli-main/messages` 返回 71+ 条含早期 🪿 对话 |
| 历史端点 | `GET /api/sessions/cli-main/messages`（W228）可用，返回 `{ok, session, messages:[{role,content}]}` | curl 实测 200 |
| 前端启动路径 | `main.ts`/`chat.ts`/`state.ts` 无任何历史拉取；`api.ts` 无 messages 函数（W230 删"只读回放"时一并删除） | grep 全零命中 |
| 结果 | 页面刷新 → 聊天区空白，输入正常；后端数据完整无丢失 | 用户实测反馈 |

## 2. 根因

会话数据在后端持久，但前端在"启动/重连"时没有恢复步骤。SSE 只推增量（turn 期间的事件），页面刷新等于错过全部存量。不是持久化缺失，是 UI 无恢复语义。

## 3. 方案评估

| 方案 | 做法 | 优点 | 缺点/成本 | 评分 |
|---|---|---|---|---|
| **A. 启动拉取历史（推荐）** | boot 时 `GET /api/sessions/cli-main/messages` → 用现有消息组件渲染存量 → 加"以下为本次会话"分隔线 → 后续 SSE 增量照旧 | 复用现有端点与渲染组件；后端单源一致；半天级 | 需处理历史/live 衔接去重 | 五星 |
| B. SSE 历史回放流 | 连接时先推存量事件流再推增量 | 体验最平滑、单一通道 | 后端需新增 replay 序列语义（turn id/seq 对齐），成本中 | 三星 |
| C. 前端本地缓存（IndexedDB） | 客户端缓存 + 后端对账 | 离线可看、省一次请求 | 多标签页/多端不一致风险，复杂度高，收益低 | 两星 |
| D. 多会话可切换持久化 | 会话树点击 = 切换活跃会话，turn 绑定该会话 | 契合"工作区/会话树"远期形态 | 需后端活跃会话概念 + Profile 级改造，正交于通讯闭环 | 远期演进三星 |

## 4. 方案 A 落地设计要点（供实施参考）

1. **渲染上限**：只渲染最近 N 条（如 200），更早折叠为"加载更早"（端点加 `limit/before` 参数，后端按序截取）。
2. **live 衔接去重**：以 turn id / 事件序号去重；SSE `turn_start` 事件到来时若与已恢复尾部重叠，跳过已渲染部分。
3. **恢复标记**：分隔线「以下为本次会话（刷新前历史见上）」。
4. **失败降级**：端点 404/超时 → 空视图 + 提示，不崩溃（沿用现有优雅降级模式）。
5. **与 context trim 无关**：trim 只裁模型上下文窗口，不动持久化日志（W220 语义），历史恢复不受影响。
6. **安全**：恢复内容走现有 marked 渲染管线（同 live 消息），不新增注入面。

## 5. 建议

- **立即做 A**：工作量小、直击用户痛点；配合后端 `limit` 参数一起上。
- D（会话切换）等"工作区/会话树"的后续需求明确后再评估，不与通讯闭环混批。
